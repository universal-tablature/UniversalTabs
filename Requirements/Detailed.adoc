= Universal Tabs Detailed Requirements: Initial Sketch

Status: exploratory, non-normative.

This document sketches a data model for review. Field names and JSON shapes are
examples, not a stable serialization contract. Once agreed, individual
requirements will be made normative and assigned stable identifiers.

== Design principles

* Describe operations at the instrument boundary through actuators, geometry,
  interactions, techniques, states, and gestures.
* Keep tracks, performers, and instrument instances independent.
* Separate persistent configuration from excitation.
* Permit explicit low-level events as well as profile-defined gestures.
* Keep the common event envelope small; put instrument semantics in referenced
  profiles.

== Document structure

A document has three broad sections: file metadata, performance setup, and
event tracks. The `utab` section identifies the file and format. The `setup`
section contains definitions and configuration required to interpret events.
The `tracks` section contains the actual performance events.

[source,json]
----
{
  "utab": {
    "version": "0.1-draft",
    "documentId": "example-song",
    "title": "Example Song",
    "authors": ["Example Author"]
  },
  "setup": {
    "profiles": [
      {
        "id": "profile:fretted-string",
        "source": "profiles/fretted-string.json"
      }
    ],
    "instruments": [
      {
        "id": "guitar-1",
        "name": "Acoustic Guitar",
        "profile": "profile:fretted-string",
        "configuration": {
          "tuning": ["E2", "A2", "D3", "G3", "B3", "E4"]
        }
      }
    ],
    "performers": [
      { "id": "performer:alex", "name": "Alex" }
    ],
    "time": {
      "meter": { "numerator": 4, "denominator": 4 },
      "tempo": { "quarterNotesPerMinute": 120 }
    }
  },
  "tracks": [
    {
      "id": "track:guitar-1",
      "name": "Acoustic Guitar",
      "instrument": "guitar-1",
      "performer": "performer:alex",
      "events": [
        {
          "id": "event:1",
          "at": { "musical": { "measure": 1, "beat": 1 } },
          "action": "pluck",
          "target": "strings[1]"
        }
      ]
    }
  ]
}
----

`setup` is not merely descriptive metadata. Profile selection, instrument
configuration, and the time map directly affect the interpretation of track
events. Profiles may be referenced or embedded, subject to rules still to be
defined.

Events are nested in tracks. The containing track supplies their instrument
and optional performer assignment, so individual events do not repeat those
references. Multiple tracks may reference the same instrument, and a performer
may be assigned to multiple tracks.

Open questions:

* Are profiles embedded, referenced, or both?
* Which identifiers must be globally unique rather than document-local?
* Can a track change its instrument or performer assignment, or should that
  require a separate track?
* Are non-performance tracks, such as lyrics, annotations, or conductor cues,
  part of the core format or extensions?

== Profile structure

A profile separates instrument actuators, physical geometry, permitted
interaction methods, techniques, and optional performer defaults. An
instrument instance binds these abstract profile elements to a specific
configuration.

[source,json]
----
{
  "id": "profile:fretted-string",
  "profileVersion": "0.1-draft",
  "actuators": {
    "strings": {
      "count": 6
    }
  },
  "geometry": {
    "frets": {
      "movable": false
    }
  },
  "interactions": {
    "stopString": {
      "effectors": ["finger"]
    },
    "exciteString": {
      "effectors": ["finger", "pick"]
    },
    "dampString": {
      "effectors": ["finger", "palm"]
    }
  },
  "performerDefaults": {
    "stoppingFingers": 4
  },
  "techniques": {
    "bend": {
      "target": "string",
      "parameters": {
        "pitchOffset": {
          "type": "interval",
          "continuous": true
        }
      }
    },
    "slide": { "target": "string" },
    "vibrato": { "target": "string" },
    "hammerOn": {
      "target": "string",
      "requires": { "stringSounding": true },
      "changes": ["stoppingPosition"]
    },
    "pullOff": { "target": "string" },
    "harmonic": { "target": "string" }
  }
}
----

Frets belong to geometry because they constrain valid stopping positions but
are not normally actuated. Fingers, picks, and palms are effectors used by
interaction methods rather than instrument actuators. The performer default of
four stopping fingers is overridable and is not an instrument constraint.

Technique entries range from declarations to fuller definitions in this early
sketch. A normative profile must define each technique's targets, parameters,
preconditions, and state effects sufficiently for consistent interpretation.

Open questions:

* Should actuator groups be addressable targets or only selection shortcuts?
* How are derived actuators and coupled controls represented?
* Should profiles inherit from other profiles or compose named capabilities?
* Should interaction effectors use a core vocabulary, profile-local values, or
  namespaced identifiers?

== Bitset actuator groups

Banks of predominantly binary controls, including the keys and holes of many
woodwind instruments, can be represented as a bitset. The profile assigns a
stable meaning to each bit position; the core format does not assign musical
meaning to a bit by itself.

[source,json]
----
{
  "id": "profile:saxophone",
  "actuators": {
    "keys": {
      "representation": "bitset",
      "width": 24,
      "bits": [
        { "index": 0, "actuator": "octave-key" },
        { "index": 1, "actuator": "left-hand-b" },
        { "index": 2, "actuator": "left-hand-a" },
        { "index": 3, "actuator": "left-hand-g" }
      ],
      "bitValue": {
        "0": "released",
        "1": "pressed"
      }
    }
  }
}
----

Bitsets are serialized as hexadecimal strings rather than JSON numbers. This
preserves the declared width and avoids dependence on an implementation's
integer precision. Bit index zero corresponds to the least-significant bit of
the decoded value. A conforming serializer should pad the value to the number
of hexadecimal digits required by the declared width.

[source,json]
----
{
  "target": "keys",
  "parameter": "state",
  "value": { "encoding": "hex", "data": "0x00000f" }
}
----

A bitset value is a complete snapshot of the group. Explicit masked updates
may be added if event size or independent control tracks make them necessary,
but their precedence and conflict rules must first be specified.

Bitsets are not suitable for every wind-instrument control. Partially covered
tone holes, breath pressure, embouchure, slides, and other continuous inputs
remain ordinary discrete or continuous actuators. Profiles may therefore
combine bitset groups with individually addressed controls.

Open questions:

* Should a profile be permitted to reserve unnamed bits for future expansion?
* Is hexadecimal sufficient, or is a base64 encoding needed for very large
  actuator banks?
* Should common named fingerings be aliases for bitset values?

== Common event envelope

Every event needs an identity, time, type, and payload. Its containing track
provides the instrument and optional performer context. Duration is optional
because some events are instantaneous or persist until explicitly changed.

[source,json]
----
{
  "id": "event:42",
  "at": { "musical": { "measure": 8, "beat": "3/2" } },
  "type": "action",
  "action": "pluck",
  "target": { "group": "strings", "index": 2 },
  "parameters": { "intensity": 0.72 }
}
----

Candidate rules:

* Event order MUST be determined by time, not JSON array position.
* Simultaneous events MUST be representable without artificial ordering.
* Values with physical dimensions MUST declare or inherit defined units.
* Profiles MUST define the meaning and allowed range of action parameters.

== Persistent state and excitation

Chord fingering is state applied to individual strings. A subsequent strum is
a separate gesture over some or all strings. The example array is the `events`
value of a guitar track.

[source,json]
----
[
  {
    "id": "event:chord-c",
    "at": { "musical": { "measure": 1, "beat": 1 } },
    "type": "state",
    "changes": [
      { "target": "strings[1]", "parameter": "position", "value": 0 },
      { "target": "strings[2]", "parameter": "position", "value": 1 },
      { "target": "strings[3]", "parameter": "position", "value": 0 },
      { "target": "strings[4]", "parameter": "position", "value": 2 },
      { "target": "strings[5]", "parameter": "position", "value": 3 },
      { "target": "strings[6]", "parameter": "muted", "value": true }
    ]
  },
  {
    "id": "event:strum-c",
    "at": { "musical": { "measure": 1, "beat": 1 } },
    "type": "gesture",
    "gesture": "strum",
    "target": "strings[1..5]",
    "parameters": {
      "order": "ascending-index",
      "spread": { "value": 45, "unit": "ms" },
      "intensity": 0.8
    }
  }
]
----

The string numbering and the meaning of ascending index must be declared by
the instrument profile rather than assumed by the core format.

== Independent controls on wind instruments

Fingering and breath are separate actuator state. This permits a fingering
change during sustained airflow and allows breath contours to be represented
without repeating the fingering. The example array belongs to a saxophone
track.

[source,json]
----
[
  {
    "id": "event:sax-fingering",
    "at": { "absolute": { "value": 2.4, "unit": "s" } },
    "type": "state",
    "changes": [
      {
        "target": "keys",
        "parameter": "state",
        "value": { "encoding": "hex", "data": "0x000003" }
      }
    ]
  },
  {
    "id": "event:sax-breath",
    "at": { "absolute": { "value": 2.4, "unit": "s" } },
    "duration": { "value": 0.8, "unit": "s" },
    "type": "control",
    "target": "breath",
    "parameter": "pressure",
    "curve": [
      { "offset": 0.0, "value": 0.0 },
      { "offset": 0.08, "value": 0.7 },
      { "offset": 0.7, "value": 0.65 },
      { "offset": 0.8, "value": 0.0 }
    ]
  }
]
----

The pressure values above are normalized. Profiles may instead require a
physical unit where that distinction is meaningful and measurable.

== Gestures and expansion

Gestures compactly encode common patterns such as arpeggios, rolls, and
trills. A profile must define enough semantics for consistent interpretation.

[source,json]
----
{
  "id": "event:arpeggio-1",
  "at": { "musical": { "measure": 4, "beat": 1 } },
  "duration": { "musical": "1/2" },
  "type": "gesture",
  "gesture": "arpeggio",
  "target": "strings[1..6]",
  "parameters": {
    "pattern": [6, 4, 3, 2, 1, 2, 3, 4],
    "timing": "even"
  }
}
----

Open questions:

* Must every gesture expand deterministically into primitive actions?
* Can a gesture intentionally retain performer discretion?
* If discretion is allowed, how is its permitted range expressed?

== Time domains

Musical and absolute time require an explicit mapping. A tempo map is the
initial candidate for metrically organized music.

[source,json]
----
{
  "time": {
    "musical": {
      "ticksPerQuarter": 960,
      "meterMap": [
        { "at": { "measure": 1 }, "numerator": 4, "denominator": 4 }
      ],
      "tempoMap": [
        { "at": { "measure": 1, "beat": 1 }, "quarterNotesPerMinute": 120 }
      ]
    },
    "absoluteOrigin": { "value": 0, "unit": "s" }
  }
}
----

Using both rational musical positions and integer ticks may be redundant. The
detailed time model must select a canonical representation and specify exact
conversion and rounding behavior.

== Constraints

Instrument constraints describe the instrument, independent of who or what
operates it.

[source,json]
----
{
  "constraints": [
    {
      "type": "mutualExclusion",
      "targets": ["pedals[sustain]", "pedals[practice]"]
    },
    {
      "type": "transitionTime",
      "from": { "action": "released", "target": "valves[1]" },
      "to": { "action": "pressed", "target": "valves[1]" },
      "minimum": { "value": 8, "unit": "ms" }
    }
  ]
}
----

Performer-capability profiles may add anatomical or ability constraints, but
those constraints are optional and must not alter the meaning of instrument
events.

== Topics still requiring detailed requirements

* stable identifier and reference syntax;
* profile composition and extension namespaces;
* pitch, tuning, temperament, and pitch-result derivation;
* articulation and technique vocabularies;
* continuous-curve interpolation;
* event precedence and conflicting state changes;
* uncertainty, alternatives, and editorial annotations;
* profile discovery, embedding, and integrity verification;
* compatibility and unknown-field behavior;
* schema and semantic validation; and
* conformance classes and test fixtures.

== Exploratory examples

The self-contained files under `Examples/` exercise the current sketch with a
handpan, nyckelharpa, guitar, cello, drum kit, and xylophone. They are design
examples rather than conformance fixtures; unresolved fields and semantics in
these files should drive subsequent detailed requirements.
